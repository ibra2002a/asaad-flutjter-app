# VENDORA — منصة الجملة للتجار في العراق

> **Trade Smarter. Grow Faster.**

منصة B2B لربط المشترين التجاريين (محلات، مطاعم، شركات) بموردي الجملة، مبنية بـ **Next.js + TypeScript + Tailwind CSS + Supabase**، واجهة عربية RTL، وتعمل على الجوال والتابلت والحاسوب.

هذا الملف يشرح **التشغيل خطوة بخطوة** (بدون خبرة تقنية)، ثم النشر على Vercel، والنسخ الاحتياطي، والاختبارات. خطة المشروع والقرارات والافتراضات موجودة في [`docs/PLAN.md`](docs/PLAN.md).

## 3. إعداد قاعدة البيانات (Supabase) — مرة واحدة

### 3.1 إنشاء المشروع
1. ادخل إلى Supabase واضغط **New project**.
2. اختر اسماً (مثلاً `vendora-pilot`)، واختر **Region** قريباً (مثلاً Frankfurt أو Singapore).
3. احفظ **كلمة مرور قاعدة البيانات** في مكان آمن (مدير كلمات مرور).
4. انتظر حتى ينتهي الإنشاء.

### 3.2 تشغيل ملفات قاعدة البيانات بالترتيب
ادخل إلى **SQL Editor** ثم **New query**. افتح كل ملف من المجلد `supabase/migrations/` **بالترتيب** وانسخ محتواه والصقه في المحرر ثم اضغط **Run**:

| الترتيب | الملف | المحتوى |
|---|---|---|
| 1 | `20260601000001_schema.sql` | الجداول والقيود والفهارس ومصفوفة الحالات |
| 2 | `20260601000002_security.sql` | سياسات RLS والصلاحيات وعرض الموردين العام |
| 3 | `20260601000003_functions.sql` | منطق الأعمال: الطلبات، الحالات، العمولات، النزاعات، التدقيق |
| 4 | `20260601000004_storage.sql` | مخزن صور المنتجات وقواعد الرفع |
| 5 | `20260601000005_reference_data.sql` | المحافظات، الفئات، قاعدة العمولة التجريبية 4% |

> الملفات تُنفَّذ مرة واحدة. إذا ظهر خطأ، لا تكمل؛ أرسل نص الخطأ للمطور.

### 3.3 إعداد المصادقة (Authentication)
1. **Authentication → URL Configuration**:
   - **Site URL**: عنوان موقعك، مثلاً `https://vendora.vercel.app` (أو `http://localhost:3000` أثناء التجربة).
   - **Redirect URLs**: أضف `https://vendora.vercel.app/auth/callback` و `http://localhost:3000/auth/callback`.
2. **Authentication → Providers → Email**: أبقِ البريد وكلمة المرور مفعّلين. يُنصح بإبقاء **Confirm email** مفعّلاً.
3. **Authentication → Sign In / Providers → Password**: الحد الأدنى 8 أحرف (يتحقق منه التطبيق أيضاً).

### 3.4 أخذ المفاتيح
من **Project Settings → API**:
- **Project URL** → ستضعه في `NEXT_PUBLIC_SUPABASE_URL`.
- **anon / publishable key** → ستضعه في `NEXT_PUBLIC_SUPABASE_ANON_KEY`. هذا المفتاح **آمن للمتصفح** لأن سياسات RLS تحمي البيانات.
- **service_role key** → **سري جداً**. يُستخدم فقط على جهازك لسكربت البيانات التجريبية. **لا تضعه في Vercel ولا تكتبه في أي ملف يُرفع إلى GitHub.**

## 4. تشغيل المشروع محلياً

```bash
cd vendora
cp .env.example .env.local      # ثم افتح .env.local وضع القيم الحقيقية
npm install
npm run dev                     # ثم افتح http://localhost:3000
```

ملف `.env.local` يُتجاهل تلقائياً من Git. لا تشاركه مع أحد.

### 4.1 إنشاء بيانات تجريبية (اختياري، للتجربة فقط)
```bash
NEXT_PUBLIC_SUPABASE_URL=https://xxxx.supabase.co \
SUPABASE_SERVICE_ROLE_KEY=... \
SEED_DEMO_PASSWORD='choose-a-long-password' \
npm run seed:demo
```
يُنشئ حسابات بنطاق `@vendora.test` ومنتجات تبدأ أسماؤها بـ **[تجريبي]**. **لا تشغّله على المشروع الحقيقي للبيع.**

### 4.2 إنشاء أول مدير
1. سجّل حساباً عادياً من صفحة **إنشاء حساب** في الموقع.
2. من Supabase: **Authentication → Users** وانسخ معرّف (UUID) الحساب.
3. من **SQL Editor** نفّذ (غيّر المعرّف):
```sql
update public.profiles set role = 'admin' where id = 'PASTE-USER-UUID-HERE';
```
> هذا الإجراء الوحيد الذي يُنفَّذ من SQL لأن التطبيق لا يسمح بترقية الحسابات ذاتياً. لاحظ أن ترقية الحسابات تتم لاحقاً من صفحة **المستخدمون** في لوحة المدير.

### 4.3 دور فريق العمليات
نفس الطريقة أعلاه، مع استبدال `admin` بـ `ops`.

## 5. النشر على Vercel

1. ارفع الكود إلى GitHub.
2. في Vercel: **Add New → Project** واختر المستودع.
3. **Root Directory**: اختر `vendora` (مهم، لأن المشروع داخل هذا المجلد).
4. **Environment Variables** — أضف:

| المفتاح | القيمة | ملاحظة |
|---|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | رابط المشروع | عام |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | المفتاح anon | عام (آمن) |
| `NEXT_PUBLIC_SITE_URL` | `https://اسم-مشروعك.vercel.app` | يُستخدم في رابط تأكيد البريد |

> **لا تضف `SUPABASE_SERVICE_ROLE_KEY` إلى Vercel.** التطبيق لا يحتاجه.

5. اضغط **Deploy**. بعد النشر، حدّث **Site URL** في Supabase كما في القسم 3.3.

### 5.1 قبل إطلاق حقيقي (قائمة تحقق)
- [ ] غيّر نسبة العمولة من **لوحة الإدارة → العمولات** (النسبة 4% تجريبية) ثم فعّل القاعدة الجديدة.
- [ ] راجع مدة نافذة الاعتراض (افتراضياً 48 ساعة).
- [ ] تأكد أن البريد الإلكتروني يصل فعلاً (تسجيل حساب تجريبي).
- [ ] جرّب دورة كاملة: مشتري يطلب ← مورد يقبل ويجهّز ويسلّم ← ops يكمل ← تقرير العمولة.
- [ ] جرّب نشر منتج بحساب مورد غير معتمد (يجب ألا يظهر للعامة).
- [ ] فعّل النسخ الاحتياطي (القسم 7).

## 6. الاختبارات

```bash
npm test                 # اختبارات الوحدات (منطق الأعمال، التحقق من المدخلات، الصور، السلة)
npm run typecheck        # فحص الأنواع TypeScript
npm run lint             # فحص الكود
npm run build            # بناء الإنتاج
```

**اختبارات قاعدة البيانات والصلاحيات** (تشغّل كل الهجرات على قاعدة بيانات محلية مؤقتة وتختبر RLS من حسابات مختلفة):

```bash
# على جهازك أو في GitHub Actions: قاعدة بيانات PostgreSQL محلية فقط
createdb vendora_test
TEST_DATABASE_URL=postgresql://postgres@127.0.0.1:5432/vendora_test \
VENDORA_DB_TEST_CONFIRM=yes \
npm run test:db
```
> السكربت **يحذف** مخططات `public` و`auth` و`storage` في القاعدة المحددة، لذلك يرفض العمل بدون `VENDORA_DB_TEST_CONFIRM=yes`. لا تشغّله أبداً على قاعدة Supabase.

ملف CI جاهز في `.github/workflows/vendora-ci.yml` يشغّل كل ما سبق عند كل تعديل.

## 7. النسخ الاحتياطي والاستعادة

- **Supabase (الخطة المجانية)** لا تتضمن نسخاً احتياطية يومية مُدارة. للإنتاج الفعلي يُنصح بالترقية إلى خطة مدفوعة فيها **Point-in-time recovery** أو النسخ اليومي.
- **نسخة يدوية أو مجدولة** من جهازك (تحتاج `pg_dump` وهو جزء من PostgreSQL):
```bash
# رابط الاتصال: Project Settings → Database → Connection string (URI)
pg_dump "postgresql://postgres.xxxx:PASSWORD@aws-0-REGION.pooler.supabase.com:5432/postgres" \
  --no-owner --format=custom --file "vendora-$(date +%F).dump"
```
- احفظ الملفات في مكان آمن مشفّر، ولا ترفعها إلى Git (ملفات `*.dump` مُستثناة).
- **الاستعادة** على مشروع جديد: `pg_restore --no-owner -d "POSTGRES_URL" vendora-YYYY-MM-DD.dump`.
- جرّب الاستعادة على مشروع تجريبي مرة كل شهر على الأقل.
- صور المنتجات موجودة في Supabase Storage وتُنسخ بنفس الطريقة من لوحة Supabase (Storage → Download) أو عبر أدوات Supabase CLI.

## 8. الأمان في نقاط سريعة

- **كل صلاحية تُفرض في قاعدة البيانات** (RLS + دوال SECURITY DEFINER)، وليس في الواجهة فقط. لا يستطيع المتصفح تعديل الأسعار أو العمولات أو الحالات أو الأدوار مباشرة.
- **الأسعار** تُقرأ من قاعدة البيانات عند إرسال الطلب. الكميات والمنتجات فقط هي ما يرسله المتصفح.
- **العمولة** تُحسب في قاعدة البيانات، وقيد `CHECK` يتحقق من صحة المعادلة.
- **رفع الصور**: يُتحقق من محتوى الملف (توقيعه البرمجي) وليس من امتداده، وحجمه 5 ميغابايت كحد أقصى، وأنواع JPG/PNG/WebP فقط.
- **تحديد المعدل (Rate limiting)**: الطلبات (20 كل 10 دقائق لكل مستخدم) ورفع الصور (60 كل ساعة) عبر جدول في قاعدة البيانات `rate_limit_hits`. تسجيل الدخول محمي بحماية Supabase Auth المدمجة.
- **مفاتيح**: لا توجد أسرار في الكود أو في ملفات Git. `.env*` مُستثناة.
- **رأس الأمان**: HSTS وX-Frame-Options وX-Content-Type-Options مُفعّلة في `next.config.ts`.
- **لا يُظهر النظام** رسائل خطأ داخلية للمستخدم، ويعرض رسالة عامة مع رمز محدد للحالات المعروفة.

## 10. القيود المعروفة في النسخة التجريبية

- التوصيل في **بغداد** للتجربة (البيانات تدعم كل المحافظات).
- الطلب من **مورد واحد** لكل طلب.
- لا توجد محفظة أو حجز أموال: الدفع يتم خارج المنصة، والمنصة تسجّل التسوية فقط.
- الاسترداد بعد الإلغاء يتم خارج المنصة ويُسجَّل في ملاحظة القرار.
- لا يوجد إرجاع للبضاعة كمسار منفصل (يُعالَج عبر النزاع).
- لا توجد إشعارات بريدية أو SMS مخصصة (يعتمد على رسائل Supabase الافتراضية للتأكيد).
- لا توجد مهمة مجدولة تُكمل الطلبات تلقائياً؛ يُكمل فريق العمليات الطلب بعد التأكد من التسليم.
