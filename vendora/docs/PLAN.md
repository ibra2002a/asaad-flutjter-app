# VENDORA — خطة المشروع والقرارات والتحقق

هذا المستند يوثّق الخطة (المرحلة 1)، والافتراضات، وقواعد الأعمال، ومصفوفة الصلاحيات، وما تم التحقق منه فعلياً، وما يبقى.

---

## 1. الخطة (المرحلة 1)

**الهدف:** نسخة MVP قابلة للتشغيل لمنصة جملة B2B في بغداد، تربط المشترين التجاريين بالموردين، بميزانية منخفضة (خدمات مجانية أو شبه مجانية).

**المكدس:** Next.js 16 (App Router) + TypeScript + Tailwind CSS 4 + Supabase (PostgreSQL، Auth، Storage) + Vercel للنشر. التحقق بـ zod، وقاعدة البيانات هي المرجع النهائي للصلاحيات.

**المراحل:**

| المرحلة | المحتوى | الحالة |
|---|---|---|
| 1 | فحص البيئة، الخطة، الهيكل | مكتملة |
| 2 | نظام التصميم، الهيكل، التنقل، RTL | مكتملة (تحقق بصري على 390px و1280px) |
| 3 | المصادقة، المخطط، الهجرات، RLS | مكتملة (36 اختبار أمان على PostgreSQL) |
| 4 | الكتالوج، الموردون، الصور | مكتملة |
| 5 | السلة، الطلبات، الحالات، العمولات | مكتملة |
| 6 | الإدارة، الأمان، سجل التدقيق | مكتملة |
| 7 | بيانات تجريبية، اختبارات، توثيق، CI | مكتملة (32 اختبار وحدات + اختبارات قاعدة البيانات) |

**هيكل الملفات:** انظر قسم "هيكل المشروع" في `README.md`.

**البيئة التي تم فحصها:** Linux، Node 22، PostgreSQL 16 محلي، Chromium (Playwright) للتحقق البصري. لا يوجد وصول إلى Supabase أو Vercel الحقيقيين من بيئة التطوير.

## 2. الافتراضات الموثقة

1. **حساب واحد لكل مستخدم** ونشاط تجاري واحد لكل حساب. الحساب يُنشأ مع النشاط (`businesses.owner_id` فريد).
2. **التسجيل الذاتي** يقتصر على مشتر أو مورد. أدوار ops و admin لا تُمنح ذاتياً؛ الترقية الأولى بـ SQL والبقية من لوحة الإدارة.
3. **الموردون** يبدأون في حالة `pending` ولا يستطيعون نشر منتجات أو استقبال طلبات قبل الاعتماد. يُسمح لهم بحفظ مسودات.
4. **الحسابات المعلّقة/الموقوفة** تُحجب من الكتالوج العام؛ الموقوف لا يستطيع معالجة الطلبات.
5. **المحافظات**: 18 محافظة عراقية في جدول `cities`، والتجربة مقتصرة على بغداد (علامة `is_pilot`). المورد يحدد محافظات تغطيته، والمشتري يطلب فقط إلى محافظة تغطيها كل منتجات الطلب.
6. **الطلب من مورد واحد** لكل طلب (المتطلب الأول للإصدار).
7. **الأسعار بالدينار كأعداد صحيحة** (`bigint`). العرض بأرقام لاتينية مع "د.ع".
8. **الدفع خارج المنصة** (نقداً، تحويل بنكي، أو دفع آجل بموجب اتفاق). المنصة لا تحتفظ بالأموال.
9. **رسوم التوصيل** صفر في النسخة الحالية وتُحدَّد مع المورد؛ لا تدخل في العمولة إلا إذا فعّلتها القاعدة.
10. **الخصومات**: الحقل موجود (`discount_iqd`) ومُدمج في حساب "المبلغ الخاضع للعمولة"، لكن لا توجد واجهة لإدخال خصومات بعد.
11. **صور المنتجات** في bucket عام بمسارات UUID عشوائية؛ الصورة غير المنشورة لا تُعرض في الكتالوج لكن رابطها يبقى قابلاً للوصول لمن يعرفه. إذا كان هذا غير مقبول، يُحوَّل الـ bucket إلى خاص مع روابط موقّعة.
12. **تأكيد البريد** مفعّل افتراضياً في Supabase Auth.
13. **لا توجد مهام مجدولة**: إكمال الطلب يدوياً من فريق العمليات، وتسديد العمولات يدوياً مع مرجع تحويل.
14. **الاختبارات** تعمل على PostgreSQL محلي بمخطط مُحاكى لـ `auth` و`storage` (ملف `supabase/test/local-shim.sql`). هذا يكفي لاختبار RLS ومنطق الدوال، لكن لا يغني عن اختبار على Supabase الحقيقي.

## 3. دورة الطلب والحالات

الحالات: `submitted`، `accepted`، `preparing`، `out_for_delivery`، `delivered`، `completed`، `cancelled`، `disputed`.

| من | إلى | من يستطيع |
|---|---|---|
| submitted | accepted | المورد، ops، admin |
| submitted | cancelled | المشتري، المورد، ops، admin |
| accepted | preparing | المورد، admin |
| accepted | cancelled | المورد، ops، admin |
| preparing | out_for_delivery | المورد، admin |
| preparing | cancelled | المورد، ops، admin |
| out_for_delivery | delivered | المورد، admin |
| delivered | completed | **ops، admin فقط** |
| delivered / completed | disputed | المشتري (ضمن النافذة)، ops، admin — عبر `open_dispute` |
| disputed | completed | ops، admin (قرار النزاع) |
| disputed | cancelled | ops، admin (قرار النزاع) |

**القواعد المطبّقة:**
- **المشتري والمورد لا يستطيعان إكمال الطلب مباشرة** (المتطلب الصريح).
- **المشتري يلغي** فقط قبل قبول المورد. بعد القبول يتواصل مع ops.
- **الإلغاء من الإدارة** يتطلب ملاحظة مكتوبة (3 أحرف على الأقل).
- **كل تغيير** يُسجَّل في `order_events` بالمنفِّذ والدور والوقت والملاحظة. السجل append-only بالتصميم (لا توجد صلاحية تعديل له).
- **المصدر الوحيد للحقيقة** جدول `order_transitions` في قاعدة البيانات. نسخة TypeScript في `src/lib/orders/rules.ts` تُستخدم لعرض الأزرار فقط، واختبار الوحدات يفشل إذا اختلفت عن ملف SQL.

## 4. قواعد العمولة

- **القاعدة قابلة للتكوين** من لوحة العمولات: النسبة بنقاط أساس (400 = 4%)، ومدة نافذة الاعتراض بالساعات (افتراضي 48)، وهل تدخل رسوم التوصيل (افتراضي لا).
- **القاعدة تتغير بإنشاء قاعدة جديدة** وتفعيلها؛ لا يوجد تعديل للقاعدة القديمة. قاعدة واحدة فقط نشطة (فهرس فريد جزئي).
- **الحساب:** `المبلغ المؤهل = المجموع الفرعي − الخصم (+ التوصيل إن فُعّل)`، والعمولة = `floor((المؤهل × نقاط_الأساس + 5000) / 10000)` أي تقريب نصف لأعلى بالدينار الكامل. الحساب في قاعدة البيانات، والقيد `CHECK` يرفض أي قيمة لا تطابق المعادلة. المتصفح لا يرسل أي مبلغ عمولة.
- **عمولة واحدة لكل طلب** (`commissions.order_id` فريد) و`INSERT ... ON CONFLICT DO NOTHING`. تكرار طلب الإكمال لا ينشئ سجلاً ثانياً (مُختبَر).
- **تُنشأ العمولة عند الإكمال** بحالة `pending` وتاريخ استحقاق `payable_at = completed_at + نافذة الاعتراض`.
- **النزاع** على طلب مكتمل ضمن النافذة يحوّل العمولة إلى `on_hold`. قرار الإبقاء يعيدها `pending`، وقرار الإلغاء يُلغيها `voided` بسبب `order_cancelled`.
- **المستحقة للتسديد** = `pending` و`payable_at <= now()`. التسديد اليدوي يتطلب مرجعاً (تحويل/إيصال) ويُسجَّل `paid_at`.
- **التقرير** مجمّع حسب المورد: طلبات، مبيعات مؤهلة، بانتظار النافذة، مستحقة، معلّقة، مُسددة، وتصدير CSV محمي من حقن المعادلات (`=`, `+`, `-`, `@`).
- **الإرجاع (Returns)**: غير مُنفَّذ كمسار مستقل. يُعالَج عبر النزاع والإلغاء، والاسترداد يتم خارج المنصة ويُوثَّق في ملاحظة القرار.

## 6. ضوابط الأمان

| المتطلب | التنفيذ |
|---|---|
| التحقق من المدخلات في الخادم | zod في كل Server Action، ثم قيود CHECK وتحقق داخل الدوال |
| RLS على كل الجداول | مفعّل على كل جدول في `public`، مع الصلاحيات الدنيا (`revoke all` ثم `grant`) |
| منع تصعيد الصلاحيات | `profiles.role` و`businesses.status` غير قابلين للتعديل من العميل (column grants) |
| الأسرار | مفتاح service role لا يُقرأ في التطبيق، ولا يظهر في ملفات الـ bundle (تم فحصه) |
| تحديد المعدل | جدول `rate_limit_hits` + دالة `consume_rate_limit` للطلبات والرفع |
| رفع الصور | التحقق من التوقيع البرمجي، الحجم 5MB، bucket بـ MIME محدد، مجلد لكل مستخدم، 5 صور كحد أقصى |
| منع التصيد المفتوح | مسار إعادة التوجيه بعد الدخول مقيّد بمسار نسبي |
| CSV | حماية من حقن الصيغ |
| رؤوس HTTP | HSTS، X-Frame-Options، nosniff، Referrer-Policy، Permissions-Policy |
| سجل التدقيق | مشغلات تسجّل: الاعتماد، الأدوار، التفعيل، القواعد، العمولات، النزاعات، الفئات، المحافظات، مع المنفِّذ والملاحظة |
| الأخطاء | رموز `ERR_*` مترجمة للعربية، والنصوص الخام لا تظهر للمستخدم |
| تسجيل الدخول | رسالة واحدة للبريد أو كلمة المرور الخاطئة (منع كشف الحسابات) |

## 7. ما تم التحقق منه فعلياً

| الفحص | النتيجة |
|---|---|
| هجرات قاعدة البيانات على PostgreSQL 16 | تُنفَّذ بالترتيب بلا أخطاء |
| اختبارات الأمان وقواعد الأعمال (`npm run test:db`) | **36/36 ناجحة** |
| اختبارات الوحدات (`npm test`) | **32/32 ناجحة** (العمولة، الحالات، السلة، التحقق، الصور، الأخطاء) |
| اتساق مصفوفة الحالات بين SQL وTypeScript | مُختبر آلياً |
| فحص الأنواع (`tsc --noEmit`) | ناجح |
| ESLint | ناجح بدون أخطاء |
| بناء الإنتاج (`next build`) | ناجح، 30 مساراً (صفحات وAPI) |
| تشغيل الخادم وفحص المسارات | الصفحات العامة 200، المسارات المحمية تُعاد توجيهها للدخول |
| الاتجاه RTL وأول الصفحة `lang="ar" dir="rtl"` | مُتحقق |
| عرض الجوال (390px) وسطح المكتب (1280px) | لا يوجد تمرير أفقي بعد الإصلاح؛ تم فحص الصفحات الأربع الأساسية بصرياً |
| عدم تسريب مفتاح service role إلى الـ bundle | مُتحقق |

### ما لم يتم التحقق منه (يجب فعله قبل الإطلاق)
- **تشغيل الهجرات على مشروع Supabase حقيقي** (تحتاج صلاحيات المشروع).
- **تدفق التسجيل الحقيقي مع إرسال البريد** وصفحة `/auth/callback`.
- **رفع صورة فعلية** إلى Storage الحقيقي والتحقق من سياسة الـ bucket.
- **سكربت البيانات التجريبية** على مشروع حقيقي (تم كتابته، لم يُشغَّل على Supabase).
- **النشر على Vercel** وإعداد متغيرات البيئة.
- **اختبار على أجهزة حقيقية** (iOS/Android) ومتصفحات متعددة، واختبار الأداء تحت حمل.
- **اختبارات End-to-End** بمتصفح كامل ضد Supabase حقيقي (لم تُكتب بعد).

## 8. تقدير الميزانية

- **Supabase**: الخطة المجانية كافية للتجربة المحدودة. الانتقال إلى Pro (نحو 25 دولاراً شهرياً) ضروري عند الإنتاج الفعلي للنسخ الاحتياطي اليومي.
- **Vercel**: الخطة المجانية (Hobby) مخصصة للاستخدام غير التجاري وفق شروط Vercel. للتشغيل التجاري غالباً تحتاج خطة Pro، وتحقق من الشروط الحالية.
- **الدومين**: تكلفة سنوية بسيطة.
- **التطوير**: الميزانية المستهدفة (10–30 مليون دينار) تكفي لاستكمال المرحلة الثانية (تطبيق جوال أو تحسينات) وتشغيل التجربة، مع بقاء البنية التحتية بتكلفة شهرية قليلة في بداية التشغيل.

## 9. ما يبقى بعد MVP (مرشّح للمرحلة التالية)

1. اختبارات End-to-End بـ Playwright ضد مشروع Supabase اختباري.
2. إشعارات بريد/واتساب عند تغيّر حالة الطلب.
3. مهمة مجدولة لإكمال الطلبات بعد مدة من التسليم دون اعتراض (بقرار تجاري).
4. مسار إرجاع منفصل وأثره على العمولة.
5. طلبات من موردين متعددين (تقسيم الطلب) — يتطلب تغيير نموذج الطلب.
6. تعديل الكميات بعد تأكيد المورد، وتعديل السعر على طلب مفتوح.
7. لوحات أداء للمورد (مبيعات، معدل الإلغاء).
8. توسيع التغطية إلى محافظات أخرى (البيانات جاهزة؛ يلزم تعديل `is_pilot` وعرض التغطية).
9. دعم الدارك مود والإنجليزية (الواجهة عربية فقط حالياً).
